# 🔗 نظام مركز الدعم الفني المتكامل
## Technical Support Center Integration System

---

## 📋 نظرة عامة (Overview)

يوفر هذا النظام تكاملًا شاملًا بين:
- **مركز الدعم الفني** (Support Center) ← استقبال طلبات الدعم من فرق الميدان
- **أوامر الصيانة** (Work Orders) ← تتبع المهام والإجراءات
- **فرق الصيانة** (Maintenance Teams) ← توزيع ذكي للطلبات
- **قاعدة المعرفة الفنية** (Knowledge Base) ← قوالب استجابة معيارية

## 🔄 سير العمل (Workflow)

### المرحلة 1: استقبال طلب الدعم
```
1. فريق ميداني → يرسل طلب دعم (إما عبر تطبيق أو المنصة)
2. تطبيق الويب → ينشئ WorkOrder جديد بحالة "pending"
3. النظام → يسجل:
   - title_ar: العنوان بالعربية
   - asset_name: اسم الأصل (مثل: Pump-A-01)
   - work_type: نوع المهمة (pump_maintenance, valve_check, etc.)
   - priority: درجة الأولوية (critical, high, medium, low)
   - notes: ملاحظات إضافية
   - created_at: وقت الإنشاء
```

### المرحلة 2: التوزيع الذكي على الفرق
```
1. مسؤول مركز الدعم → يختار الفريق المناسب من قائمة منسدلة
2. النظام → يتحقق من:
   - تخصص الفريق (فريق الكهرباء ← أعطال كهربائية)
   - توفر الفريق
   - سجل الأداء
3. تحديث WorkOrder:
   - assigned_team: اسم الفريق
   - status: "assigned" (تم التوزيع)
   - assigned_at: وقت التوزيع
```

### المرحلة 3: اقتراح القوالب الذكية
```
1. النظام يحلل:
   - نوع العطل (fault_code: PMD-001, VLV-002, etc.)
   - نوع المهمة (work_type)
   - الأصل المعني (asset)
   - الفريق المخصص

2. يقترح القوالب الأكثر ملاءمة:
   - قوالب مخصصة للفريق (applicableTeams filter)
   - قوالب مرتبطة بالعطل (faultCodes mapping)
   - مرتبة حسب الاستخدام السابق (team frequency ranking)
```

### المرحلة 4: الرد الموحد
```
خيار 1: إدراج في المسودة
- تحرير: يختار قالب → "إدراج في الرد"
- يظهر محتوى القالب في صندوق المسودة
- يمكن إضافة/تعديل قبل الإرسال

خيار 2: إرسال فوري
- تحرير: يختار قالب → "إرسال فوري"
- يُرسل محتوى القالب مباشرة كرسالة
- النظام يسجل استخدام القالب (لتحسين الترتيب لاحقًا)
```

### المرحلة 5: تحديثات الحالة
```
مدير الدعم يحدّث الحالة:
  pending    → assigned      (تم التوزيع)
  assigned   → in_progress   (الفريق بدأ العمل)
  in_progress → resolved     (تم الحل)
  resolved   → closed        (تم التوثيق والإغلاق)
```

## 💡 قوالب المعرفة الفنية (Knowledge Templates)

### مثال: قالب "فصل كهربائي متكرر"

```javascript
{
  id: 'electrical-trip',
  title: 'فصل كهربائي متكرر',
  tags: ['electrical', 'trip', 'كهرباء', 'قاطع'],
  faultCodes: ['ELC-003'],
  applicableTeams: ['فريق الكهرباء', 'Electrical Team', 'الفريق الكهربائي'],
  content: `خطة المعالجة:
1) مراجعة سجل القواطع والحمايات (Overcurrent/Undervoltage).
2) قياس تيار التشغيل ومقارنته بالتصميم.
3) فحص التوصيلات ونقاط السخونة.
4) عدم إعادة التشغيل قبل تحديد السبب الجذري واعتماد مسؤول السلامة.`
}
```

**المميزات:**
- ✅ عربي كامل (مع إمكانية الترجمة)
- ✅ مرتبط برمز عطل محدد (فهرسة أفضل)
- ✅ محدود الفرق المناسبة (توزيع ذكي)
- ✅ محتوى معياري موثق (ضمان الجودة)

## 🔗 الربط الذكي (Smart Linking)

### 1. ربط العطل بالقالب
```
العطل: ELC-003 (فصل كهربائي متكرر)
  ↓
القالب: 'electrical-trip'
  ↓
الفريق: 'فريق الكهرباء'
```

### 2. ربط الفريق بالقوالب
```
الفريق: 'فريق الكهرباء'
  ↓
القوالب المتاحة:
  • فصل كهربائي متكرر (ELC-003)
  • خلل قراءة حساس (SNS-005) ← إذا كان المستشعر كهربائي
```

### 3. ربط التكرار بالترتيب
```
فريق: 'فريق الكهرباء'
الاستخدام:
  • electrical-trip: 8x (الأكثر استخدامًا)
  • sensor-fault: 2x (الأقل استخدامًا)
  
الترتيب:
  1. electrical-trip ← يظهر أولًا
  2. sensor-fault ← يظهر ثانيًا
```

## ✅ معايير النجاح (Success Criteria)

### 1. الاستقبال
- ✅ يتم إنشاء WorkOrder جديد تلقائيًا عند استقبال الطلب
- ✅ يتم حفظ جميع البيانات (العنوان، الأولوية، الأصل، الملاحظات)

### 2. التوزيع
- ✅ التوزيع الذكي بناءً على تخصص الفريق
- ✅ تحديث الحالة من "pending" إلى "assigned"
- ✅ تسجيل وقت التوزيع

### 3. الاقتراح
- ✅ اقتراح قوالب مناسبة للفريق والعطل
- ✅ ترتيب القوالس حسب الاستخدام السابق
- ✅ عرض 3-5 قوالب بحد أقصى

### 4. الرد
- ✅ خيار الإدراج في المسودة (للتعديل)
- ✅ خيار الإرسال الفوري (للسرعة)
- ✅ تسجيل استخدام القالب

### 5. التحديث
- ✅ الانتقال بين الحالات: pending → assigned → in_progress → resolved → closed
- ✅ تسجيل جميع التحديثات مع الوقت والمسؤول

### 6. الإغلاق
- ✅ توثيق السبب والحل
- ✅ حفظ الوقت الكلي (من الإنشاء إلى الإغلاق)
- ✅ إمكانية إعادة فتح إذا لزم الأمر

## 🧪 نتائج الاختبار

### اختبار 1: ربط الأعطال
```
✅ PMD-001 → pump-low-pressure
✅ VLV-002 → valve-stuck
✅ ELC-003 → electrical-trip
✅ PLP-004 → pipeline-leak
✅ SNS-005 → sensor-fault
النتيجة: جميع الأعطال مرتبطة بقوالب
```

### اختبار 2: تخصص الفرق
```
✅ فريق الصيانة الميكانيكية → قالب المضخات
✅ فريق التحكم → قالب الصمامات
✅ فريق الكهرباء → قالب العطل الكهربائي
النتيجة: جميع الفرق لديها قوالس متخصصة
```

### اختبار 3: الفرز الذكي
```
✅ العطل + الفريق = القالب الأنسب
✅ نفس العطل + فريق مختلف = قالب مختلف مناسب
النتيجة: الفرز الذكي يعمل بكفاءة
```

### اختبار 4: تتبع الاستخدام
```
✅ فريق الكهرباء استخدمت "electrical-trip" 8x
✅ ترتيب أفضلي يُعطي الأولوية للقوالس الأكثر استخدامًا
النتيجة: التعلم من الاستخدام يحسّن التجربة
```

### اختبار E2E
```
✅ الاستقبال → التوزيع → الرد → التحديث → الإغلاق
✅ جميع الخطوات تعمل بسلاسة
النتيجة: مسار العمل الكامل جاهز للإنتاج
```

## 🚀 الخطوات التالية

1. **تجربة حقيقية** على النظام الحي بـ:
   - فرق ميدانية حقيقية
   - أعطال حقيقية
   - تسجيل الوقت والأداء

2. **جمع المقاييس**:
   - متوسط وقت الاستجابة (Response Time)
   - معدل الحل من المحاولة الأولى (First Resolution Rate)
   - رضا الفريق عن القوالس (Template Satisfaction)

3. **التحسين المستمر**:
   - إضافة قوالس جديدة بناءً على الأعطال المتكررة
   - تحديث القوالس الموجودة بناءً على التغذية الراجعة
   - توسيع الفرق والأعطال المدعومة
